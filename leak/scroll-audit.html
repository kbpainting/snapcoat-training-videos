The short version

Two root causes explain almost everything. Both are single-place fixes, not a 70-page slog. Tested live at 3440, 2560, 1440 and 1280 wide against the real app, not just by reading CSS.

Root cause 1 · affects every page

A global rule traps the mouse wheel

index.css:3632–3641 applies overscroll-behavior: contain to every element whose class contains overflow-y-auto. The block is titled “iOS SCROLL & MOMENTUM OPTIMIZATION” — but it has no media query and no platform guard, so it applies to desktop too.

/* iOS SCROLL & MOMENTUM OPTIMIZATION  ← the intent
   Smooth, native-feeling scroll on all iOS devices */

.overflow-auto, .overflow-y-auto, .overflow-x-auto,
[class*="overflow-auto"], [class*="overflow-y-auto"],
[class*="overflow-x-auto"] {
  -webkit-overflow-scrolling: touch;
  overscroll-behavior: contain;   ← blocks scroll chaining
}

contain is exactly right on touch: it stops rubber-banding and stops the page behind a modal from moving. On a mouse wheel it does something else — when an inner list reaches its end, the page behind refuses to keep scrolling. You have to physically move the pointer off the list to continue. That is the “multiple scrolls that don’t work together” feeling.

Root cause 2 · 22 dialogs across 18 files

The wheel-death pattern is back, in bulk

A Radix DialogContent that is itself overflow-y-auto, containing another overflow-y-auto, kills the wheel inside the dialog. Scrollbar drag still works, which is precisely why it survives testing.

This is the same defect Greg Chung reported as bug #48 on the Production Rates modal in July. That instance was fixed; the pattern was never swept up elsewhere. Of 328 DialogContent instances in the app, 22 still have it.

<DialogContent className="max-w-4xl max-h-[80vh] overflow-y-auto">   ← scroller 1
  <div className="max-h-[400px] overflow-y-auto">                    ← scroller 2
                                                    wheel dies here

Honest caveat

When I forced overscroll-behavior: auto to confirm the cause, only /projects/calendar visibly started chaining. Synthetic wheel events in headless Chrome don’t reproduce scroll-chaining reliably, so that arm of the test is weak evidence. The reproduction above is solid, and the CSS spec is unambiguous about what contain does — but the fix will want your eyes on a real machine, not just my say-so.

Secondary findings

28 pages

h-screen inside a shell that is already full height

The app shell is h-[100dvh] overflow-hidden and the only intended scroller is its <main>. 28 pages that render inside it still declare h-screen / min-h-screen, which forces 100vh of height into a box that is already shorter than the viewport (the header eats the difference). Worst: project-pipeline, sales-pipeline, projects/reports at 3 each.

Not a false positive: I checked. 136 other pages use h-screen legitimately because they are standalone full-viewport routes (auth, blog, compare, customer portal) that never mount the shell. Those are excluded.

12 pages

Multiple page-level scrollers in one file

sales/sop.tsx has 13, sales/proposal-builder-redesign.tsx 7, settings/production-rates.tsx 6. Most are inside dialogs, which is where they overlap with root cause 2.

Clean

Ultrawide is fine horizontally

Zero horizontal overflow at 3440 or 2560 on any page tested. No fixed-width containers spilling, no sideways scrollbars. The ultrawide problems are vertical only.

Worth a look

/notifications renders without the shell

No <main> element at any viewport, so it sits outside the standard layout. Probably deliberate, but it means it doesn’t inherit the shell’s scroll behaviour.

Proposed fix order

  • 1 — Scope the iOS block to touch devices. Wrap it in @media (hover:none) and (pointer:coarse) so contain applies to phones and tablets and desktop gets normal chaining. One edit, fixes the systemic symptom everywhere at once. Keep contain unconditionally on modals/drawers, where it is correct on every platform.
  • 2 — Sweep the 22 dialogs. Remove the inner overflow-y-auto so the DialogContent is the single scroller, exactly as bug #48 was fixed. Mobile keeps its scroll through the existing .dialog-body-scroll media-query CSS.
  • 3 — Replace h-screen with h-full on the 28 in-shell pages. Mechanical, but each one needs a look because a few use it for intentional full-bleed sections.
  • 4 — Re-measure at all four widths and diff against this baseline.

1 and 2 are the ones that will actually change how the app feels. 3 is hygiene that prevents the next regression.
